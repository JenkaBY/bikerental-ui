# bikerental-ui — Angular 21 multi-project workspace, browser front end for a bike rental shop POS

## Summary

- Three independently deployable Angular SPAs (`gateway`, `admin`, `operator`) plus one shared Angular library (`shared`), built from a single workspace and one commit.
- All communication is synchronous HTTP/REST against one external Spring Boot backend (out of this repo), reached through an `ng-openapi`-generated client; a development-only SSE stream carries a simulated clock for the "time travel" testing feature.
- Two deployment targets share one build definition: GitHub Pages (static hosting, cross-origin to a test API) and a Caddy container image (`pi` target, same-origin to the production API, published to GHCR and rolled out by a separate repository via `repository_dispatch`).
- Authentication is OIDC (`angular-auth-oidc-client`), one client id per authenticated SPA (`admin`, `operator`); `gateway` is unauthenticated.
- No backend code, database, message broker, or infrastructure-as-code lives in this repository — the backend is an external dependency identified only by its OpenAPI spec and base URL.

## Services

SERVICE_NAME: gateway
TYPE: Frontend
PURPOSE: Unauthenticated, locale-aware landing SPA served at the site root; the only page that answers a bare domain request, and it lets a person choose admin or operator.
OVERVIEW_REF: `overview.md` (single document covering all four workspace projects; see its "Projects and Folder Map" and "Components" sections for `gateway`)
ENTRY_POINT: `projects/gateway/src/main.ts`
EXPOSES:
  - PROTOCOL: HTTP
    ENDPOINT_OR_TOPIC: `/` (site root; dev server port 4200)
    DESCRIPTION: Compiled static bundle serving the application-chooser page (`HomeComponent`)
CONSUMES:
  - PROTOCOL: HTTP
    ENDPOINT_OR_TOPIC: `{apiUrl}/actuator/health`, `{apiUrl}/actuator/info`
    FROM_SERVICE: bikerental-backend
    DESCRIPTION: Periodic health/info polling (`HealthPollerService`, every `environment.healthPollIntervalMs`)
  - PROTOCOL: HTTP
    ENDPOINT_OR_TOPIC: `/admin` (dev-server proxy target `http://localhost:4201`)
    FROM_SERVICE: admin
    DESCRIPTION: Local-development-only proxy so the gateway origin can reach the admin dev server (`proxy.conf.json`); not present in any built artifact
  - PROTOCOL: HTTP
    ENDPOINT_OR_TOPIC: `/operator` (dev-server proxy target `http://localhost:4202`)
    FROM_SERVICE: operator
    DESCRIPTION: Local-development-only proxy, same purpose as above

## Architectural Patterns

- PATTERN: Monorepo workspace with one shared library, no independent versioning
  SCOPE: Whole repository
  EVIDENCE: A single `angular.json` and `package.json` govern four projects; `shared` has no version of its own and is consumed only via a TypeScript path alias, never published

- PATTERN: Three-layer data pipeline enforced by the shared library's structure
  SCOPE: shared
  EVIDENCE: `core/api/generated/` (raw, code-generated) → `core/mappers/` (pure static converters) → `core/models/` (UI domain types); components import only from `core/models/`

- PATTERN: Lint-enforced module boundary
  SCOPE: gateway, admin, operator, shared
  EVIDENCE: `no-restricted-imports` in `eslint.config.js` blocks deep `projects/shared/src/**` paths and the `@store.*` alias from the three apps, and blocks the `@bikerental/shared` barrel from inside `shared` itself (cyclic-init hazard)

- PATTERN: One build definition, two deployment targets differentiated only by configuration
  SCOPE: gateway, admin, operator
  EVIDENCE: The `build` job matrix in `.github/workflows/build-and-deploy.yml` varies only `configuration`, `env_file` and `api_url` between `pages` and `pi`; no build flags differ, so the public demo cannot drift from production in anything but environment values

- PATTERN: Deployed-path abstraction instead of hardcoded cross-app URLs
  SCOPE: gateway, admin, operator, shared
  EVIDENCE: `DeployedPath` (`shared/utils/deployed-path.ts`) derives origin/prefix/app/locale/route from `document.baseURI` at runtime, because the URL prefix is present on GitHub Pages and absent on `pi`

- PATTERN: OIDC per-SPA client identity, shared identity provider
  SCOPE: admin, operator
  EVIDENCE: `provideOidcAuth('bike-rental-admin')` and `provideOidcAuth('bike-rental-operator')` in each app's `app.config.ts`; `gateway` has no `provideOidcAuth` call at all

- PATTERN: Global error-toast interceptor with an explicit local-handling opt-out
  SCOPE: gateway, admin, operator (via shared)
  EVIDENCE: `errorInterceptor` toasts every failed request by default; callers that render the error themselves pass `suppressErrorNotification()` to avoid a double notification

- PATTERN: Backend as sole source of truth for authorization
  SCOPE: admin, operator, bikerental-backend
  EVIDENCE: Route guards (`adminGuard`, `operatorGuard`) read role claims decoded client-side from the access token purely to gate navigation; every API call still carries the bearer token for the backend to authorize independently

- PATTERN: Same build artifact, different trust boundary per deployment target
  SCOPE: gateway, admin, operator, bikerental-backend
  EVIDENCE: The `pages` target is cross-origin to its API (needs CORS) while the `pi` target is same-origin behind one router (no CORS, no preflights) — documented in `README.md`'s deployment table

- PATTERN: Feature flag disables an entire communication channel
  SCOPE: admin, operator, bikerental-backend
  EVIDENCE: The SSE time-travel stream (`SSE_PROVIDER`, `TimeTravelStore`) is only wired up when `environment.timeTravelEnabled` is true; every checked-in environment file sets it `false`, so the channel is dormant in every shipped build

## Security Topology

AUTHN_AUTHZ:
  - Authentication: OIDC authorization-code flow via `angular-auth-oidc-client`, one client id per authenticated SPA (`bike-rental-admin`, `bike-rental-operator`); `gateway` has no authentication.
  - Token attachment: `apiAuthInterceptor` attaches the bearer token to API-bound requests only, with a single refresh-and-replay on a 401 response.
  - Authorization: role and `mustChangePassword` claims are decoded client-side from the access token (`readAccessTokenClaims`) and gate route activation only (`authGuard`, `mustChangePasswordGuard`, `adminGuard`, `operatorGuard`, `customerProfileGuard`); the backend is the actual authorization authority for every API call.
  - Password policy (length, composition, confirmation match) is enforced client-side before submission and re-validated by the backend.

TRUST_BOUNDARIES:
  - Browser (any of the three SPAs) ↔ `bikerental-backend`: the only trust boundary this repository has code on either side of; every business rule and every persisted fact lives past this boundary.
  - `pages` deployment ↔ its API: cross-origin — the browser enforces CORS, and the backend must allow the Pages origin explicitly.
  - `pi` deployment ↔ its API: same-origin, behind one reverse-router — no CORS, no preflight requests, because both are served from the same public host.
  - This repository's CI ↔ the backend's own repository (`JenkaBY/bike-rental`): a one-way `repository_dispatch` carrying only an image tag; the CI process never receives a response and holds no long-lived credential to that repository (`PI_DEPLOY_TOKEN` is scoped to triggering the dispatch, not to code access).
  - GHCR ↔ the production host: the UI image is public, so the host pulls it without a stored credential in this repository's CI.

KNOWN_RISKS:
  - OIDC access/refresh tokens are held in `sessionStorage` by `angular-auth-oidc-client`; any successful XSS in a shipped bundle can read them.
  - `environment.lan.ts` hardcodes a private LAN IP address and is checked into the repository.
  - The `pages` (public demo) target is built against a real API host taken from a repository variable (`BIKE_RENTAL_TEST_API`), so the public demo is a live client of a real backend instance, not a mock.
  - Client-visible role gating (`adminGuard`/`operatorGuard`) is a navigation convenience only; a user who tampers with client state can reach a route's UI shell but not any data the backend refuses to authorize.
  - The `disable_service_worker` workflow input is a fleet-wide, irreversible-until-rerun kill switch (replaces `ngsw-worker.js` with Angular's safety worker on every operator client); it is manually triggered but carries real blast radius across every installed PWA instance.

## Deployment Topology

DEPLOYMENT_MODEL: One Git commit, one CI run, two independent deployment targets built by the same job matrix and gated by the same lint/test/build checks.

CONTAINER_RUNTIME: Docker (`caddy:2-alpine` base image), used only for the `pi` target; the `pages` target has no container — it is a static file tree.

ORCHESTRATION: NONE in this repository. The `pi` target's image is pushed to GHCR and this repository's involvement ends with a `repository_dispatch` to the backend's own repository (`JenkaBY/bike-rental`), which is responsible for pulling and running the new image on the production host; no Kubernetes/Compose/Helm/Terraform artifacts exist here.

SERVICES_AND_PORTS:
  - Local development: gateway `http://localhost:4200` (with proxy to the other two), admin `http://localhost:4201`, operator `http://localhost:4202`; backend expected at `http://localhost:8080`.
  - `pages` target: static files at `https://jenkaby.github.io/bikerental-ui/` — gateway at the site root (`/en/`, `/ru/`), admin at `/admin/…`, operator at `/operator/…`.
  - `pi` target: one Caddy container listening on port 8080 internally, serving gateway at `/`, admin at `/admin/`, operator at `/operator/` — no path prefix, because the container is the whole origin.

CONFIG_REFS:
  - `.github/workflows/build-and-deploy.yml` — the full pipeline: `quality` → `test` → `build` (matrix `pages`/`pi`) → `ci` gate → `deploy` (Pages) / `image` (GHCR) → `notify-server` (cross-repo dispatch).
  - `docker/Dockerfile` — copies the pre-built `staging/{gateway,admin,operator}` trees into a non-root (`1201:1201`) Caddy container.
  - `scripts/gen-ui-config.mjs` + `scripts/apps.mjs` — generate `docker/Caddyfile.generated` from the assembled `staging/` tree's actual locale directories, failing the build if a required locale or app is missing.
  - `scripts/verify-ngsw-integrity.mjs` — the last step to touch `staging/` before upload; re-hashes every file an `ngsw.json` pins and fails the build on any mismatch.
  - `angular.json` — per-project `build`/`serve` targets, base-href-free in source (base href is passed as a CLI flag per target in CI).
